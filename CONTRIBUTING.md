# Contributing to Doordarshan

*Where every meeting feels connected.*

Thank you for your interest in contributing to Doordarshan. Contributions of all sizes are welcome, from fixing bugs and improving tests to refining real-time communication and backend architecture.

Doordarshan is an evolving open-source video conferencing project built with FastAPI, WebSockets, WebRTC, and PostgreSQL. Contributions should help keep the project focused, understandable, and maintainable.

## Before You Begin

- Read the [README](README.md) to understand the project, its architecture, and local setup.
- Check existing issues and pull requests before starting substantial work.
- For larger changes, open an issue or discussion first to align on the problem and proposed approach.
- Be respectful and constructive when communicating with other contributors.

## Development Setup

### Requirements

- Python 3.11 or later
- PostgreSQL
- Git
- A modern browser with WebRTC support

### Set Up the Project

Clone the repository and enter its directory:

```bash
git clone https://github.com/aryanap07/doordarshan.git
cd doordarshan
```

Create and activate a virtual environment.

**Linux / macOS**

```bash
python3 -m venv .venv
source .venv/bin/activate
```

**Windows PowerShell**

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

Install the project with its development dependencies:

```bash
python -m pip install --upgrade pip
pip install -e ".[dev]"
```

Create your local environment file:

**Linux / macOS**

```bash
cp .env.example .env
```

**Windows PowerShell**

```powershell
Copy-Item .env.example .env
```

Configure the required values in `.env`, including your PostgreSQL connection and TURN service credentials. Never commit `.env`, secrets, or production credentials.

Apply the existing database migrations:

```bash
alembic upgrade head
```

For the full configuration and run instructions, refer to the [README](README.md).

## Contribution Workflow

1. **Fork** the repository.
2. **Create a branch** from the appropriate base branch.
3. **Make a focused change** that addresses one problem or feature.
4. **Add or update tests** for behavior that has changed.
5. **Run the relevant quality checks.**
6. **Update documentation or migrations** when needed.
7. **Open a pull request** describing the change and its impact.

Use clear branch names, for example:

```text
fix/websocket-disconnect
feat/meeting-validation
docs/contributing-guide
test/room-lifecycle
```

## Code Guidelines

### Keep Changes Focused

- Follow the existing project structure and naming conventions.
- Keep API endpoints, business services, persistence logic, and WebSocket handling appropriately separated.
- Prefer readable, explicit implementations over unnecessary abstraction.
- Avoid unrelated refactoring in bug fixes or feature pull requests.
- Do not introduce a new dependency unless it is needed; explain the reason in your pull request.

### Python Quality

Do not reformat or rewrite unrelated files. Use the repository's configured tools and settings.

Run the available checks:

```bash
ruff check .
black --check .
mypy app
pytest -ra
```

You can also use the project's Makefile to run the complete development check:

```bash
make check
```

If a check is unavailable or fails because of an unrelated existing issue, mention that clearly in your pull request.

### Tests

- Add regression tests for bug fixes where practical.
- Test successful behavior and relevant failure cases.
- Keep tests deterministic and independent of external services where possible.
- Cover API validation, authentication, room lifecycle, and WebSocket behavior when those areas change.
- Do not claim that tests pass unless you have run them.

Run the test suite:

```bash
pytest -ra
```

Run tests with coverage:

```bash
pytest --cov=app --cov-report=term-missing
```

### Database Changes

If you change SQLAlchemy models or database structure, include the corresponding Alembic migration.

Create a migration:

```bash
alembic revision --autogenerate -m "describe the change"
```

Review autogenerated migrations before committing them. Autogeneration is a starting point, not a substitute for reviewing the migration.

Apply migrations locally:

```bash
alembic upgrade head
```

If a migration changes existing data or could affect deployed environments, explain the implications in the pull request. Do not modify or delete existing migration history without a clear reason and prior discussion.

### API, WebSockets, and WebRTC

For changes to real-time communication:

- Preserve clear message schemas and validation.
- Consider authentication, authorization, connection lifecycle, and disconnect handling.
- Handle invalid or unexpected messages safely.
- Avoid logging tokens, credentials, or private message content.
- Explain protocol or payload changes and their compatibility implications.
- Do not assume that signaling success guarantees a working media connection; consider the relevant connection states and failure paths.

## Pull Request Checklist

Before submitting, make sure your pull request:

- [ ] Explains the problem and the proposed change.
- [ ] Keeps the scope focused.
- [ ] Includes tests or explains why they are not applicable.
- [ ] Passes relevant linting, formatting, type-checking, and test commands.
- [ ] Includes an Alembic migration when the database schema changes.
- [ ] Updates documentation when behavior or setup changes.
- [ ] Contains no secrets, credentials, generated artifacts, or unrelated changes.
- [ ] Notes any limitations, trade-offs, or follow-up work.

A useful pull request description includes **Context**, **Changes**, **Testing**, and **Risks or Follow-up**.

## Reporting Bugs and Proposing Features

When reporting a bug, include:

- What you expected to happen.
- What actually happened.
- Steps to reproduce the issue.
- Relevant logs or error messages, with secrets and personal information removed.
- Your environment details when they may affect reproduction.

For feature proposals, describe the use case, the behavior you have in mind, and any impact on existing APIs, WebSocket messages, database models, or meeting workflows.

For suspected security vulnerabilities, **do not open a public issue**. Follow the private reporting process in [SECURITY.md](SECURITY.md).

## Project Direction

Doordarshan is in active development. Not every planned feature is implemented, and proposed changes may need discussion before they are accepted. Keep contributions aligned with the current architecture and explain substantial design changes before investing in a large implementation.
